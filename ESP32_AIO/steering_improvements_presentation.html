Improvement 1 of 6

Stiction Boost

The Problem

In cold weather, with heavy implements, or on tight turns, the steering system can get stuck — the motor is running but the wheel isn't actually moving. The system just sits there with error piling up.

🎬 Orange = motor effort · Blue = wheel movement · Red zone = boost fires to break free

The Fix

The firmware now watches for stalls. If the wheel hasn't moved meaningfully after a configurable timeout, it adds a temporary boost to break free — then backs off once movement is detected.

SettingWhat it does
stictionBoostSize of the extra kick (0–1.0)
stictionTimeoutHow long to wait before boosting (ms)
stictionThresholdMin movement to count as "not stuck" (°)
Improvement 2 of 6

Error-Dependent Minimum PWM

The Problem

Motor drivers have a minimum power level before they can actually move. Set too high → wheel overshoots and oscillates. Set too low → motor stalls under load far from target.

🎬 Fixed high minPWM (red) overshoots and hunts · Adaptive minPWM (green) settles cleanly

The Fix

The firmware now uses two different minimum power levels:

  • Far from target: higher minimum — enough muscle to overcome resistance
  • Close to target: lower minimum — gentle enough to avoid overshoot
SettingWhat it does
minPWMfarMin power when error is large
minPWMnearMin power when close to target
minPWMFarThresholdError distance splitting the two zones (°)
Improvement 3 of 6

Anti-Windup

The Problem: "Integral Windup"

The PID controller has a memory of past error (the "I" term). When the system is held or blocked for a long time, that memory overloads. When released, the motor overshoots wildly.

🎬 Left: integral overloads → big overshoot · Right: cap limits buildup → smooth release

The Fix

Anti-windup caps how much memory can accumulate. Once the motor is at maximum effort, the system stops adding to the memory — so when released, it responds promptly without overcorrecting.

SettingWhat it does
enableAntiWindupTurn this protection on/off
antiWindupThresholdFraction of max output where cap kicks in (e.g. 0.8 = 80%)
Improvement 4 of 6

Input Filtering

The Problem: Sensor Noise

The wheel angle sensor (WAS) has tiny electrical jitter and vibration noise. The derivative term in the PID reacts to rapid changes — noise makes it overreact, causing a buzzy, oscillating motor command.

🎬 Raw WAS signal (orange, noisy) vs filtered input the PID actually sees (blue, smooth)

The Fix

A smoothing filter is applied to the sensor reading before the PID sees it. Noise is averaged out, so the controller sees gradual, meaningful changes rather than jitter.

Same principle as a noise-cancelling microphone — let the real signal through, reject the static.

SettingWhat it does
pidInputFiltFilter strength (0 = off, 1 = max smoothing). Higher = smoother but slower response.
Improvement 5 of 6

Deadband Preservation

What It Does

The deadband defines a small "close enough" zone around the target angle. When the wheel is within that zone, the motor is commanded to zero — stop trying to make micro-corrections.

🎬 Top: no deadband — hunts forever near target · Bottom: deadband zone (green) — motor stops

Why It Matters for the Other Features
  • Stops the stiction boost from firing needlessly when already at target
  • Prevents integral memory from building up while sitting still
  • Reduces motor wear from constant micro-corrections
SettingWhat it does
steerDeadbandHalf-width of the "close enough" zone in degrees (0 = disabled)
Improvement 6 of 6

Gain Scheduling

The Idea

A single fixed "aggressiveness" (Kp gain) can't be optimal for all situations:

  • Far from target: you want the motor to respond firmly and catch up quickly
  • Close to target: you want a gentle touch to avoid overshooting

🎬 Fixed gain (blue) — steady but slow · Gain-scheduled (green) — fast catch, smooth landing

The Fix

The system can now automatically switch Kp based on how far the wheel is from its target. Gains only update on zone transitions — no unnecessary recalculation every loop.

SettingWhat it does
enableGainScheduleTurn feature on/off
gainPNearKp close to target (0 = use base Kp)
gainPFarKp far from target (0 = use base Kp)
gainScheduleThresholdDistance in degrees separating near/far zones

Tuning Guide

Recommended Tuning Sequence

These features interact — tune them in order for the best result.

1
Proportional only first. Set gainI = 0, gainD = 0. Adjust gainP until steering responds briskly without obvious oscillation.
2
Add input filtering. Set pidInputFilt to a small value (e.g. 0.1–0.3) to calm sensor jitter before introducing derivative.
3
Add integral gain. Slowly raise gainI until steady-state offset is removed. Enable antiWindup at this stage.
4
Tune stiction boost if steering stalls under load. Start with a short stictionTimeout (300–500 ms) and small stictionBoost (0.15–0.25).
5
Refine near-target behaviour. Lower minPWMnear and consider enabling gainSchedule with a softer gainPNear if overshoot remains.
Summary

In Plain Terms

① Stiction Boost

Gives the motor an extra kick when it gets stuck, then backs off once moving.

② Error-Dep. Min PWM

Uses more power when far away, less power when almost there — avoids overshooting.

③ Anti-Windup

Stops the controller from "overloading" its memory when blocked, preventing a lurch when released.

④ Input Filtering

Smooths out sensor noise so the controller doesn't over-react to vibration or jitter.

⑤ Deadband

Stops the motor when "close enough" — no unnecessary hunting or micro-corrections.

⑥ Gain Scheduling

Automatically becomes more aggressive far from target and gentler when close.
